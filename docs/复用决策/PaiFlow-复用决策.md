## 详细决策

### ✅ 借鉴（思路输入）

#### 1. SSE 流式输出架构

```
PaiFlow: 前后端 SSE 连接 → zong: 直接实现
```

**借鉴点：**
- 服务端 SSE 连接管理
- 前端 EventSource 消费
- 流式响应格式定义

**zong 实现方式：**
- 使用 Spring AI Alibaba 的 `StreamingChatClient`
- 自实现 SSE 端点 `/api/agent/chat/stream`

---

#### 2. React Flow 可视化编辑器

**借鉴点：**
- 拖拽编排工作流
- 节点/边的数据模型
- 节点配置面板设计

**zong 实现方式：**
- 可选方案：
  - A. `@xyflow/react`（React Flow 的 React 版本）
  - B. 商业组件如 LogicFlow
  - C. 自己封装 SVG 组件
- 具体选型待定

---

#### 3. 工作流编排的概念模型

**借鉴点：**
- Workflow = 多个 Node + 依赖关系
- Node = LLM / 条件 / 循环 / 工具调用
- Edge = 数据流向

**zong 实现方式：**
- 不是迁移代码，而是用这个模型来定义需求
- 具体实现用 Spring AI Alibaba + PaiCLI 架构

---

### ❌ 不复用（使用框架）

| 组件 | 原因 |
|------|------|
| PaiFlow DSL 解析器 | 用 Spring AI PromptTemplate 替代 |
| PaiFlow 节点执行器 | 用 Spring AI Tool/Function Calling 替代 |
| PaiFlow Java 工作流引擎 | 处于开发版，功能不完善 |
| PaiFlow Python 后端 | 不在分析范围，且 zong 选 Java |
| PaiFlow 插件适配器体系 | 过于复杂，用 Spring AI MCP 简化 |

---

## 决策理由

```
┌─────────────────────────────────────────────────────────────────┐
│  为什么这些不留？                                                 │
├─────────────────────────────────────────────────────────────────┤
│  1. PaiFlow 是自研工作流引擎，代码是"从零设计"                      │
│     → 坑多，维护成本高                                             │
│                                                                  │
│  2. zong 选择"使用成熟框架"路线                                    │
│     → Spring AI Alibaba 有社区、有文档、有生态                      │
│                                                                  │
│  3. PaiFlow 的价值是"告诉我需要什么"，不是"给我代码"               │
│     → 工作流编排思路 → 需求输入                                     │
│     → 具体实现 → 框架 + PaiCLI 架构                               │
└─────────────────────────────────────────────────────────────────┘
```
